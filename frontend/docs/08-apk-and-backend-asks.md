# 08 · Android APK 端与后端新增需求

> 本文回答「多做 App 端（APK）要不要跟后端提新要求」，并给出可以直接转发给后端的清单。

## 1. 结论速览

**要提，但规模不大：4 项新增能力 + 3 项配置修改，业务接口一个都不用改。**

| 类别 | 项 | 形式 | 是否阻塞 APK |
| --- | --- | --- | --- |
| 新增 | Token 鉴权（access + refresh + device id） | 新接口 | 阻塞 |
| 新增 | WSS 信令服务（公网可达、加密） | 新服务 | 阻塞 |
| 新增 | TURN 临时凭证下发 | 新接口 | 阻塞 |
| 新增 | 设备推送（FCM token 注册） | 新接口 | 不阻塞首版 |
| 修改 | CORS / Origin 白名单加入 App 源 | 配置 | 阻塞 |
| 修改 | 全站 HTTPS 与 WSS | 配置 | 阻塞 |
| 修改 | WebSocket 的 Origin 校验放行 App 源 | 配置 | 阻塞 |
| 不动 | 用户资料、标签字典、匹配、话题卡、积分与榜单 | —— | —— |

**一句话给后端：** 业务接口一个都不用改，但鉴权要从 Cookie 换成 Token，并且信令与 TURN 从「可选」变成「必须有」。

## 2. 为什么 APK 会改变这些

Web 端 demo 有四个逃生口，APK 端一个都没有：

| Web 端的逃生口 | 为什么 APK 端不成立 |
| --- | --- |
| 同一浏览器开两个标签页，用 `BroadcastChannel` 当信令 | 单个 App 进程里没有第二个浏览器上下文 |
| 直接访问 localhost 或局域网 IP 调试 | 真机安装包必须访问公网域名 |
| 明文 http 也能跑 | Android 9 及以上默认禁止明文流量 |
| 后端跑在自己笔记本上 | 手机与笔记本不同网段时不可达 |

结论：**信令必须是真的服务器，TURN 必须真的有，HTTPS 与 WSS 必须真的是。**

这条直接影响 [02-frontend-scope.md](02-frontend-scope.md) 的兜底矩阵：APK 端只剩第 1 级（远端模式）与第 3 级（模拟通话），第 2 级「本地模式」在 App 上不可用。

## 3. 必须新增的后端能力

### N1 · Token 鉴权

| 项 | 内容 |
| --- | --- |
| 现状 | 不做密码 / 验证码，但**账号是真的**：`POST /api/auth/session` 带 `deviceId`，服务端按它认账号（见过复用、没见过新建），见 10 第 4.1.1 节 |
| APK 需要 | access token 加 refresh token，并绑定设备标识；支持登出 |
| 建议接口 | `/api/auth/login`、`/api/auth/refresh`、`/api/auth/logout` |
| 为什么不能沿用 Cookie | App 内的页面源是 `https://localhost`，与 Web 站点不同源。即便后端开了 CORS 且允许携带凭证，跨源 Cookie 仍受 SameSite 策略限制，在 WebView 中表现不稳定。把凭证放进 `Authorization` 头没有这个问题 |
| 附带要求 | access token 有效期建议 30 分钟，refresh token 30 天；refresh 要能撤销 |

### N2 · WSS 信令服务

| 项 | 内容 |
| --- | --- |
| 现状 | 规划里信令有三级方案，本地模式用 `BroadcastChannel`，远端模式才需要服务 |
| APK 需要 | 必须是公网可达的 `wss://`，支持鉴权、房间加入与离开、SDP 与 ICE 转发、断线重连 |
| 关键约束 | 明文 `ws://` 在 Android 上默认被拦，必须走 TLS |
| Origin 校验 | 服务端若校验 `Origin` 头，需要放行 App 的源，否则连接会被拒 |
| 消息格式 | 前端建议用 `{ type, roomId, payload }` 的 JSON 信封，具体类型见第 8 节 |

### N3 · TURN 临时凭证下发

这是 APK 端**最容易被低估**的一项。移动网络下 NAT 类型复杂，只靠 STUN 会有相当比例的房间连不通；没有 TURN，现场演示可能直接失败。

| 项 | 内容 |
| --- | --- |
| 现状 | 规划里 TURN 是「有则更好」，免费额度够 demo 用 |
| APK 需要 | 后端提供临时凭证下发，前端不再写死长期凭证 |
| 建议接口 | `/api/rtc/ice-servers`，返回 STUN 与 TURN 的地址、用户名、凭证、有效期 |
| 安全要求 | 凭证必须短期有效，且按用户或会话签发，避免被白嫖带宽 |
| 兜底 | 前端仍保留模拟通话模式，但那是保命手段，不能当主方案 |

### N4 · 设备推送

| 项 | 内容 |
| --- | --- |
| 现状 | 不需要 |
| APK 需要 | 匹配成功、收到邀请、会话提醒 |
| 建议接口 | 注册与注销设备推送标识 |
| 说明 | 首版可以先不做，用 App 内提示代替，不阻塞 10/9 |

### N5 · 最低支持版本

| 项 | 内容 |
| --- | --- |
| 用途 | App 启动时检查版本，过旧则提示升级，避免老包打不通新接口 |
| 建议接口 | `/api/app/version-policy`，返回最低版本与升级提示文案 |
| 说明 | 可延后，属于上线后的运维能力 |

## 4. 必须修改的现有配置

| 编号 | 项 | 要改什么 | 不改的后果 |
| --- | --- | --- | --- |
| M1 | CORS 白名单 | 加入 App 的源：Android 为 `https://localhost`，iOS 为 `capacitor://localhost` | 所有请求被浏览器层拦截 |
| M2 | 传输加密 | 全部接口走 HTTPS，信令走 WSS，证书有效 | Android 9 及以上直接拒绝明文请求 |
| M3 | WebSocket Origin 校验 | 放行 App 的源，或改为基于 token 鉴权而非 Origin | 信令连接被服务端拒绝 |
| M4 | 错误响应格式 | 统一成带错误码的 JSON，便于 App 端做降级与提示 | 前端只能显示通用错误 |

## 5. 明确不需要改的部分

写出来是为了避免后端过度设计：

- 用户资料与标签字典的字段结构不变。
- 匹配接口的语义不变（加入队列、拉取等待列表、确认匹配、取消）。
- 话题卡的返回结构不变，仍是三语文本加难度档。
- 积分、成就、排行榜的计算口径不变。
- 连线记录继续只存本地，APK 端也一样。

**也就是说：前端在 [07-open-questions.md](07-open-questions.md) 里定义的接口契约（Q-B1 至 Q-B5）可以原样保留，APK 只在上面的 N 与 M 两类上追加要求。**

## 6. 技术路线：Capacitor 包装，不开第二个代码库

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| Capacitor 包装现有 Web 产物 | 同一份代码产出安装包，可访问原生权限与推送 | **推荐** |
| React Native / Flutter 重写 | 两套代码、两倍工作量 | 不做，理由见 [04-tech-stack.md](04-tech-stack.md) |
| 纯 WebView 手写壳 | 要自己处理权限回调与生命周期 | 不如 Capacitor 稳 |

选 Capacitor 的理由：现有 Vite 产物直接复用，`src/` 一行不用改；麦克风权限由原生层接管；后续要加推送或原生能力有现成插件。

## 7. Web 端与 APK 端差异对照

| 能力 | Web 端 | APK 端 | 要后端配合 |
| --- | --- | --- | --- |
| 页面与路由 | 相同 | 相同 | 否 |
| 鉴权 | demo 跳过 | 必须真鉴权（N1） | 是 |
| 信令 | 三级降级 | 只剩远端与模拟（N2） | 是 |
| TURN | 可选 | 必需（N3） | 是 |
| 权限弹窗 | 浏览器弹窗 | 系统权限弹窗，首次启动时请求 | 否 |
| 通知 | 无 | 推送（N4） | 是 |
| 更新 | 刷新即最新 | 需要版本策略（N5） | 是 |

## 8. 给后端的信令消息类型建议

前端建议的最小集合，方便后端一次把协议定下来：

| 方向 | 类型 | 说明 |
| --- | --- | --- |
| 客户端发 | join | 加入房间 |
| 客户端发 | leave | 离开房间 |
| 客户端发 | offer | 发起方描述 |
| 客户端发 | answer | 应答方描述 |
| 客户端发 | ice-candidate | 网络候选 |
| 服务端发 | matched | 匹配成功，附带对端信息 |
| 服务端发 | peer-joined | 对端已进入 |
| 服务端发 | peer-left | 对端已离开 |
| 服务端发 | error | 错误码与可读信息 |

## 9. 权限与合规

Android 侧需要在清单里声明：网络访问、网络状态、麦克风、以及 Android 13 及以上的通知权限。（本产品只做语音，不申请摄像头权限。）

产品侧要一起定的：

- **隐私政策**：麦克风必须能解释用途，并明确匿名模式下的数据处理方式。
- **权限被拒的降级**：已有设计，见 [02-frontend-scope.md](02-frontend-scope.md) 的兜底矩阵，APK 端直接复用。
- **分发方式**：直接发安装包，还是上应用商店；是否涉及备案与软著，属于团队决策。
- **应用签名**：需要一个长期保存的签名密钥，丢失后无法覆盖升级。

## 10. 对 2026-10-09 排期的影响

| 建议 | 理由 |
| --- | --- |
| Web 仍是主 demo，APK 是加分项 | 现场扫码最稳，安装包有不确定性 |
| Day-1 到 Day-3 不并行做 APK | 先让 Web 主链路跑通，否则两边都半成品 |
| 包装与出包放在 P1，排在结算与成就之后 | 见 [06-roadmap.md](06-roadmap.md) |
| 后端把 N1、N2、N3 排在 2026-10-04 前完成 | 否则 APK 主链路无法联调 |

**最小可行顺序：** Web 主链路跑通 → 后端交付 N1 与 N2 → 前端接真实信令 → 后端交付 N3 → Capacitor 出包 → 真机彩排。
