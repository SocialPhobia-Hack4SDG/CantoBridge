# 07 · 待确认问题

## 1. 使用说明

本文件是前端视角的**问题清单与假设台账**。

- 每条问题都有编号（`Q-Xn`），02、03、04 里引用接口与方案时会指向这些编号。
- **每一条都带「当前默认值」**：如果没人回复，前端就按默认值开工，不阻塞排期。
- 建议在 2026-09-24 的线上会议逐条过一遍，能拍板的当场标记为已决。
- **标着「已决」的条目来自素材 4《hackathon 项目提示词》（已从本仓库移出）**（同一作者更晚的实现级指令），不需要再讨论；如需推翻，请连同 05 与 09 一起改。
- 与 Android APK 端相关的新增后端需求（Token 鉴权、WSS 信令、TURN 凭证、设备推送）单独整理在 [08-apk-and-backend-asks.md](08-apk-and-backend-asks.md)，那份文档可以直接转发给后端。
- 前后端接口的最新契约在 [09-frontend-logic-and-api.md](09-frontend-logic-and-api.md)，B 类与 C 类问题以那份文档为准。
- 身份模型的决策（不合并身份卡、改走「语言交换 + 供给优先」）记在本文件第 9 节；配套的实现交接单在 [../tasks/bc-exchange-implementation.md](../tasks/bc-exchange-implementation.md)。

## 8. G 类 · MVP 轮次的决策与假设（2026-09-23）

团队商定「Web UI 交互是第一要务，先做一个带模拟数据、重点是能跑通的 MVP」之后，前端按下面的默认值推进。**需要 9/24 会议拍板的是 Q-G2，以及 Q-G6 / Q-G8（伙伴关系从「一键保存」改成「双向申请」之后的契约）、Q-G15（取消匹配的服务端语义）、Q-G16（自定义匹配条件存哪、要不要真的影响匹配）。**

| Q-G9 | 通话记录里的「是否已保存」字段还要不要？ | **不要**：历史条目不再存这个布尔值，行上的伙伴状态一律由 `buddies` + `buddyRequests` 经 `buddyRelation()` 推导，避免「记录说已保存、伙伴表里却没有」的脱节。后端若已下发 `saved` 字段，前端会忽略 | 后端 |

## 9. 身份模型决策：不合并身份卡，改走「语言交换 + 供给优先」（2026-09-29）

### 9.1 提议与结论

组员的提议（下称 **A 方案**）：两张身份卡的「教学侧义务成分太重、难招人」，改成一张**「我能教的语言 + 我想学的语言」二合一卡**。

**结论：诊断成立，处方不采纳。** 本轮采 **B + C**，A 推迟：

| 方案 | 内容 | 本轮决定 |
| --- | --- | --- |
| **B · 回礼 + 软排序** | 母语者资料增加**可选**的「我也想练 X」（`buddyProfile.wantToLearn`）；母语者挑人时按语言互补加权排序 | ✅ 做（约 0.5 天） |
| **C · 反单边发起 + 去义工化** | 首页给学习者直接推 top 3 候选 + 一键配对；全局替换义工话术 | ✅ 做（约 0.5 天） |
| **A · 二合一身份卡** | 身份模型从「二选一」改成「教 + 学」的组合卡 | ⏸ 推迟到 2026-10-09 之后，写进 pitch 的 next steps |

实现清单（文件、字段、测试、验收）另存为交接单：[../tasks/bc-exchange-implementation.md](../tasks/bc-exchange-implementation.md)。**那份文件是实现侧的唯一入口**，本节只记决策与理由。

### 9.2 四条诊断逐条对照

「义务感太重」不是一个问题，是四个。分开看才知道该改哪个：

| 诊断 | 是否成立 | 依据 | B / C 是否命中 |
| --- | --- | --- | --- |
| ① 叙事像义工招募 | **成立** | i18n 的 `role.buddySubtitle` 与 `role.note`（`role.note` 开口先写「不是老师」，等于自己先把义务帽子戴上）；`01` 第 3.2 节「用很小的成本做一件有情绪回报的好事」 | **B 命中**（文案层） |
| ② 发起成本单边，学习者躺着等 | **成立** | 素材 4 第 8 节：初版只有「学习者等待 + 母语者挑选」，见 Q-A4 / Q-A5 | **C 命中** |
| ③ 母语者没有回报 | **成立**，但要区分要的是哪种回报 | `01` 第 3.2 节痛点 2「付出没有回响」 | **B 命中「语言回报」那一半**；「社交认可」那一半由 C 的认可体系承担 |
| ④ 身份卡要选一次，太重 | **不成立** | 「教 / 学」标签已经由身份**派生**（`intentForRole`，见 Q-G24），用户从来不选标签 | 不适用 |

③ 是唯一还没闭合的一条：**B 的收益上限由「母语者到底想要什么回报」决定**，见 Q-G29 的待确认项。

### 9.3 为什么不选 A（代价清单）

| 代价 | 说明 |
| --- | --- |
| 配对空间缩小 | 二合一之后，匹配从「单向满足」变成「双向互补」。小规模冷启动下（现场只有 3~4 个演示伙伴），可行配对近似平方级减少——**现场 demo 反而更难匹配到人**，而 C 存在的理由就是让现场一定能开聊 |
| 招人本身被拖慢 | 注册表单要从「两门语言 + 一个水平」变成「两门语言 + 两个水平」，对新用户是净负担。为了好招人而加长表单，方向是反的 |
| 丢掉粤语的中心性 | 那时产品退化成通用语言交换，必然被问「为什么不用 HelloTalk / Tandem / Speaky」，只剩「我们有卡片」答不回去。粤语是这款产品唯一的结构性壁垒 |
| 成本撞上冻结线 | A 要重写 `role` 语义、合并两份资料、`guard`、榜单双轨、两套反馈标签、35 个端点语义与 10 份文档，约 2~3 天；B + C 约 1 天。10-06 是功能冻结线 |
| —— | 但 A 的诉求里有一条是真的：**平等感**。B 用「母语者也有想要的东西」来回应，不靠取消身份差异 |

### 9.4 B 的落地规格（已决）

- **数据**：`buddyProfile` 增加 `wantToLearn`（字符串数组，**可为空**，复用 `NATIVE_LANGUAGES` 的取值，**不含粤语**）。只多 1 个字段，不动身份模型。
- **排序**：母语者挑人时，排序键 = `matchScore` + 互补加成（命中 +8，否则 0）。三条硬约束——**只加权不筛选**、**权重取 8**（`matchScore` 里一个共同标签约值 13.75 分，8 分能破平局、压不过少两个共同话题的人）、**只在母语者视角生效**（学习者的 `wantToLearn` 恒为粤语，所以学习者侧排序不变）。
- **界面**：母语者资料页多一道**可选**题（不填也能完成）；等待列表行与预览大卡上多一枚「语言互补」徽标——**徽标必须有**，否则排序变化在台上看不出来。
- **文案**：`role.note` 这类防守式文案换成正面陈述（「我讲粤语，也想练普通话 / English —— 交换。」），并删掉「义工 / 志愿 / 公益 / 奉献 / 陪伴」这类词；卡片结构与身份选择流程不变。

### 9.5 C 的落地规格（已决）

- **首页推候选人**：学习者视角在 `HomeActionCard` 下面直接列 top 3（复用 `BuddyCard` + `BuddyBrowseList`，不新增组件），每张卡一个入口按钮；母语者视角保持现状（只显示等待人数）。
- **一键配对但不越权**：机器负责排序，**人做最终确认**——点开预览、再点开始通话。这与素材 4 的「手动匹配」不冲突（Q-A4 的结论不变）。
- **后端待补**：需要一个「给学习者推荐候选」的读取口子，**实现时**并入 09 第 3.2 节与 10 第 4.4 节的接口清单（当前契约里没有它，本节不写死路径）。

### 9.6 什么时候必须回到 A（升级触发条件）

满足**任意一条**，说明 B + C 不够，必须重新评估 A：

1. 母语者要的回报明确是「**平等交换**」而不是「语言回报」或「社交认可」——B 给不了平等，A 才给；
2. B + C 上线后母语者供给仍然为 0（说明「回报」不是瓶颈，「愿不愿意花时间」才是——那么 A 也救不了，该砍的是单次时长承诺，不是身份卡）；
3. 团队能明确答出「我们和 HelloTalk / Tandem / Speaky 的区别是什么」并且答案不是「我们有 AI 话题卡」。

**若真要做 A，两个前提**：① 必须在 2026-10-06 冻结前完成；② 必须同步改 01 / 03 / 05 / 07 / 09 / 10 与 35 个端点的身份语义（`learnerProfile` 与 `buddyProfile` 合并是一次契约级改动）。
